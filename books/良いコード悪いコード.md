- 5. バラバラなデータとロジックをカプセル化する実践技法

	- 初期化ロジックの分散

	- 結果を返すために引数を使わない
		- returnを使わず計算だけする

- 6. 関心の分離という考え方を -分けて整理する-
	- インスタンス変数ごとにクラスを分割する
		- 影響スケッチ
	- 関係してそうなロジックをまとめて膨れ上がる
		- 目的ごとに分離してカプセル化する
		- 共通処理がある場合はそれ用のものを作るか
	- インターフェイスと実装の分離
		- インターフェイス：何が入力で出力かを定義する
		- 実装：中身
		- うまくできない理由
			- 入力、出力、詳細実装がない
			- ロジックを利用する側とされる側
- 7. 関心が混ざったコードを分けて整理する実践技法
	- クラスの責任
		- 単一責任の原則
		- DRY(Don't Repeat Yourself)原則の誤用
			- 同じようなロジック、似ているロジックであっても、目的が違うロジックは共通化してはいけないのです。
				- 夏セールと通常セール
	- 継承による関心の混在
		- 継承は推奨しない
		- 継承より移譲
		- コンポジション構造
			- 処理を部品化して必要な処理を別オブジェクトに任せるため
	- 関心が混在する各種事例と対処方法
		- なんでもpublic
			- パッケージは複数のファイル・クラスをまとめるグループ
			- クラスは原則としてpackage privateとする
				- pythonなら_か_init_で公開範囲を絞る
		- privateだらけ
			- クラスが様々な関心を持ってしまう
		- スマートUI
			- MVVM
				- レイヤードアーキテクチャ、クリーンアーキテクチャ、ヘキサゴナルアーキテクチャ、マイクロサービスアーキテクチャ、イベント駆動アーキテクチャ、ＤＤＤ
			- 巨大データクラス
				- データを運ぶだけならいいんでないか（値オブジェクト、DTO、設定値、フォーム入力、リクエスト入力）
			- トランザクションスクリプトパターン
			- 神クラス（God Class, Big ball of mud）
			- 丁寧にカプセル化と関心の分離を行い、100行多くても200行
- 8. 条件分岐 -迷宮化した分岐処理を解きほぐす技法-
	- ネスト
		- 早期return
			- else句は全部ifにする
	- switch文の重複
		- 修正漏れなどを引き起こす
		- 単一責任選択の原則
			- まとめる
		- interfaceの使用
			- ダックタイピング
				- 肩が何かよりメソッドを持っているか
			- ポリモーフィズム
			- 図形一覧をまとめて表示したい
			- 同じ名前の `area()` があるだけでは、Javaでは共通の型として扱えない。だから `Object` で受け取って `instanceof` するのではなく、`Shape` のような共通インターフェースを作って、`showArea(Shape shape)` と書こう
				- よくわからんけど共通の型をつくるのが難しいらしい
				- 共通インターフェイスで共通の型みたいなみたいな感じで使っている
			- ストラテジパターン
				- 取り換えたい機能をinterfaceのメソッドとして定義する
				- 目的がinterface命名の決め手
				- 取り替え対象をクラスとして設計する
				- 取り替えるクラスそれぞれにinterfaceを実装する
				- Mapで機能を切り替える
					- たいていはinterfaceで解決だが文字列、種別コード、設定値などから、対応する処理オブジェクトを選びたいときです。
					- mapへ登録してあとは共通インターフェイスで呼ぶ
				- 未実装のメソッドをコンパイラが𠮟ってくれる
				- 丁寧に値オブジェクト化する
		- interface設計の考え方
			- ・ 機能 を 取り換える 単位 を 見つける ・ インター フェイス と 実装 の 分離 に もとづき 結果 と 入力 を 整理 する ・ interface を 定義 する ・ interface を 実装 する ・ 機能 を 取り換える し くみ を つくる
		- 条件分岐の重複とネスト
			- interfaceの応用的な使い方
			- 飛ばした
		- 型の判定で分岐しないこと
		- フラグ引数
			- フラグ引数付きメソッドは、機能ごとに分離する
		- 分岐を書きそうになったらまずinterface設計。分岐ではなく機能の取り換え

	- グローバル変数

		- リフレクション
	- 技術駆動パッケージング
	- サンプルコードは参考にしつつ変更容易性の高い構造を設計する
