- なぜソフトウェアアーキテクチャが重要か
	- 非機能要件を実現するため
		- 機能要件
			- ユーザーやシステムができること
		- 非機能要件
			- 機能に限らない要件
			- 保守性などなど
	- エンジニアの効率の最大化のためにある
	- 競合への対抗
- 密結合と疎結合
	- ソフトウエアの構成要素同士の結合度合いが重要となる
	- 密結合
		- クラスやモジュールが互いの内部構造や具体的な実装に依存している状態
		- ほかのクラスの変数を直接参照したり、インスタンス自体を変数もつ
		- 関数内の変数でインスタンスをもつ
		- バリデーションをほかの関数で行ってしまう
		- 他モジュールへの変数やメソッドにアクセスし放題
		- 変更時の影響範囲がでかい
	- 疎結合
		- クラスやモジュールが互いの内部構造や具体的な実装に依存していない状態
			- インターフェイスや抽象のみへの依存、集約など
		- やりすぎてやりずらいときもある

- モノリシックアーキテクチャ
	- コードベースが単一（ひとつのリポジトリ）、全ての機能で同一プロセス内で動作、各機能が密結合
	- 小規模アプリケーションの場合
		- テストがしやすい
			- サーバー間通信がない、E2Eテストも簡単
		- デプロイしやすい
			- 複雑なコンポーネントがない、シングルバイナリ
		- スケーリングがしやすい
			- 複数インスタンスをつくるだけ
		- 開発もしやすい
			- コードベースが単一（すべてのクラス、メソッドにアクセス可能）、DBも単一（全てのデータを参照できる、整合性の担保も簡単）
	- 大規模アプリケーション開発
		- テストがつらい
			- 一部の機能を修正しただけで全体のテストが動く
		- デプロイがつらい
			- 大人数で同じコードを触るから
		- スケーリングがつらい
			- こたなるリソース要件の機能が混在
		- 開発がつらい
			- コードがでかすぎる
			- 古い技術
		- 信頼性低下
			- バグが起きやすく、特定しずらい
			- 依存箇所が多いライブラリのアプデ難易度もあがる
- マイクロサービスアーキテクチャ
	- アプリケーションが小さく独立したサービスの集合体
	- サービスごとに独立したコードベース、基盤、データベースをもつ
		- サービスは特定の機能で個別にデプロイできるソフトウェアコンポーネント
		- 外部からAPIアクセス
	- 利点
		- テストが効率的、デプロイしやすい、スケーリングが効率的、保守性が高い、信頼性向上
	- 欠点
		- マイクロサービスアーキテクチャ
			- 様々な設計パターン
			- 分散システム特有の問題への対処
		- サービスの適切な分割を考える難易度が高い
			- ほかのサービス開発に影響を与えない分割（疎結合）をする必要がある
	- 具体的にマイクロサービスアーキテクチャで考えないといけないこと
		- サービス間通信をどうするか
		- 同期API、非同期API
			- クライアントが待つか待たないか
		- 可用性を上げたければできるだけ非同期の設計に変える必要がある
		- サービス間でのデータ整合性（サーガ）
			- サーガという実現方法がある
			- 単一DBではトランズアクションのACID処理により整合性が担保可能
			- 強い整合性
				- RDBなどで保証
				- トランズアクション処理によってデータの更新が即時すべてのテーブルで反映
			- 結果整合性
				- 一時的な不一致を許容して最終的には一貫性を持つようにする
			- ダーティリード、ノンリピータブルリード
	- どうやってサービスに分割するか
		- 密結合がきつくなってからそもそも実態は変わらない
		- 疎結合だからサービスに切り出せるのである
			- 切り出しても意味ない。他のことを考えてたらもう意味ない
	- 自立チームがそれぞれ必要、内部構造を切り出してしまっている、それが目的
- モノリスvsマイクロサービス？
	- そもそもこういう構造がない
	- 初期フェーズ

		- 同期遅延による不整合が怖い

		- マイクロサービスを目指すのはだるいが生産性をあげたい
			- モジュラーモノリス

		- トレードオフ

- 設計に関する各種方法論
	- アーキテクチャスタイル
		- ソフトウェア全体の構造・依存関係の流れ、分割の指針
		- クリーンアーキテクチャ、オニオンアーキテクチャ、マイクロサービスアーキテクチャ、モノリス、ヘキサゴナルアーキテクチャ、レイヤードアーキテクチャ
	- 設計思想・アプローチ
		- 設計や実装、分割に関する思想・指針
			- オブジェクト指向、DDD、CQRS
	- 設計原則
		- クラス・モジュールの内部構造や依存のあり方に関するもの
			- SOLID原則、DRY、YAGNI
	- 設計指標
		- 設計の品質を評価する軸、設計改善の指針
		- モジュール結合度、モジュール強度、LCOM
	- 設計パターン
		- 具体的な実装方法についてのテンプレート
		- Repository, Factory, Saga, Entity
	- 注意点
		- 指標や原則に従うことを目的化するべきでない
		- 設計の方法論はパターンやテンプレートとして使うべきでない
		- 単にこれに従うだけで疎結合ができるわけでない
	- レイヤードアーキテクチャ
		- 下から上への依存はダメ
	- DDD
		- オブジェクト指向の最終形態ともいわれている
	- 設計パターンの失敗例
		- DRYやりすぎてなんでも共通化して密結合
		- 機能的強度を目指しすぎて機能を細分化してしまい逆にコードを把握しずらい
			- 人間が把握できることが大事
		- ドメインモデルの貧血症
- DDD
	- ドメインに対する理解とモデリングにしっかり取り組むことが大事
	- ドメイン
		- システムが解決しようとする業務領域・問題領域
		- 機能
	- ドメインエキスパート
		- その業務の専門家
	- ユビキタス言語
		- 開発者とドメインエキスパートなどの参画者の言葉
		- モデル、クラス名、関数名など、コード上でもそのままの言語が使われる
	- 概要
		- ドメインを深く理解し、それを中心にシステムを組み立てる設計思想
		- いろいろなものに踏み込んだもの
		- コードがドキュメントになる
		- ドメインによるモジュール分割化、意味のある疎結合化
	- 流れ
		- ドメインモデリング→実装→レビュードメインの理解
		- ドメインモデリング
			- ドメインエキスパートとの会話
			- ユビキタス言語を洗い出す
			- UMLなどでモデルと関係を整理する
			- モデルをドメインオブジェクトと対応付ける
				- ドメインオブジェクト:モデルをソフトウェアで動作するモジュールとして表現
		- 値オブジェクト
			- ライフサイクルのないオブジェクト
			- 意味やルールを持たせる
		- エンティティ
			- ライフサイクルのあるオブジェクト。一意に識別するためのIDを持つ
			- 状態変化を得ても、IDより同一性が判断される
			- どのドメインモデルに対する操作・振る舞いかということを意識する
		- 集約
			- 一貫性を保つべきエンティティや値オブジェクトをひとまとめにしたもの。
			- 集約ルートを外部とのやり取りの唯一の窓口とする
				- 内部のオブジェクトには直接外からアクセスさせない
				- ほかの集約のオブジェクトを直接参照することを禁止（IDのみ許可）
					- UserクラスがAlbumクラスのコレクションを保持しているなどはだめ
			- 集約を境界としてモジュール分割される（疎結合化）
		- ドメインサービス
			- エンティティや値オブジェクトに属さないドメイン知識に関するロジックを表現
			- 存在確認や重複確認はエンティティ自身の振る舞いとして定義するのはおかしい
		- リポジトリ、ファクトリ、仕様
	- ドメインモデルをどう隔離するか
		- 依存の関係を意識する
		- Domain層
		- Application層
		- Infrastructure層
		- データを別オブジェクトに詰めなおす作業が必要
		- ドメインモデルで逆に困ること
		- CQRS
