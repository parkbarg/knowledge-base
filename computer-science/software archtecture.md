- なぜソフトウェアアーキテクチャが重要か
	- 非機能要件を実現するため
		- 機能要件
			- ユーザーやシステムができること
		- 非機能要件
			- 機能に限らない要件
			- 保守性などなど
	- エンジニアの効率の最大化
	- 競合への対抗
- 密結合と疎結合
	- ソフトウエアの構成要素同士の結合度合いが重要となる
	- 密結合
		- クラスやモジュールが互いの内部構造や具体的な実装に依存している状態
		- ほかのクラスの変数を直接参照したり、インスタンス自体を変数もつ
		- 関数内の変数でインスタンスをもつ
		- バリデーションをほかの関数で行ってしまう
		- 他モジュールへの変数やメソッドにアクセスし放題
		- 変更時の影響範囲がでかい
	- 疎結合
		- クラスやモジュールが互いの内部構造や具体的な実装に依存していない状態
			- インターフェイスや抽象のみへの依存、集約など
		- やりすぎてやりずらいときもある
- パフォーマンス計測
	- デプロイ数
	- Four keys
		- リードタイム
		- デプロイ頻度
		- 変更失敗率
		- 平均修復時間（MTTR）
- POSA
- GoF
- モノリシックアーキテクチャ
	- コードベースが単一（ひとつのリポジトリ）、全ての機能で同一プロセス内で動作、各機能が密結合
	- 小規模アプリケーションの場合
		- テストがしやすい
			- サーバー間通信がない、E2Eテストも簡単
		- デプロイしやすい
			- 複雑なコンポーネントがない、シングルバイナリ
		- スケーリングがしやすい
			- 複数インスタンスをつくるだけ
		- 開発もしやすい
			- コードベースが単一（すべてのクラス、メソッドにアクセス可能）、DBも単一（全てのデータを参照できる、整合性の担保も簡単）
	- 大規模アプリケーション開発
		- テストがつらい
			- 一部の機能を修正しただけで全体のテストが動く
		- デプロイがつらい
			- 大人数で同じコードを触るから
		- スケーリングがつらい
			- こたなるリソース要件の機能が混在
		- 開発がつらい
			- コードがでかすぎる
			- 古い技術
		- 信頼性低下
			- バグが起きやすく、特定しずらい
			- 依存箇所が多いライブラリのアプデ難易度もあがる
